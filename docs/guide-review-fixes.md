# 1. 법적 요구 — 약관 동의 기록 (17부)

## 무엇이 문제였나

화면에는 약관 세 건의 동의 체크박스가 있는데, **동의했다는 사실이 어디에도 남지 않았습니다.**
체크를 받아 다음 단계로 넘기는 것이 전부였고 가입 요청(`SignupRequest`)에도 담기지 않았습니다.

개인정보 보호법 제22조는 동의를 각각 알리고 받으라고 하고, **동의를 받았다는 사실의 입증 책임은
사업자에게 있습니다.** 기록이 없으면 분쟁에서 증명할 방법이 없습니다.

그리고 프런트의 "다음" 버튼 비활성화는 막는 장치가 아닙니다.

```javascript
// 개발자 도구 콘솔에서
document.querySelector('button').disabled = false;
```

API 를 직접 부르면 그 버튼을 거치지도 않습니다.

## 어떻게 고쳤나

### `V4__terms_agreements.sql` (신규)

```sql
CREATE TABLE terms_agreements (
    id            INTEGER      GENERATED BY DEFAULT AS IDENTITY,
    user_id       INTEGER      NOT NULL,
    terms_key     VARCHAR(20)  NOT NULL,
    terms_version VARCHAR(40)  NOT NULL,
    agreed        BOOLEAN      NOT NULL,
    agreed_at     TIMESTAMP(6) NOT NULL,
    created_at    TIMESTAMP(6) NOT NULL,
    updated_at    TIMESTAMP(6) NOT NULL,

    CONSTRAINT pk_terms_agreements PRIMARY KEY (id),
    CONSTRAINT uk_terms_agreements_user_key UNIQUE (user_id, terms_key),
    CONSTRAINT fk_terms_agreements_user_id FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE
);
```

세 가지 결정이 들어 있습니다.

**① `terms_version` 을 함께 남깁니다.** 약관을 개정하면 그 뒤에 가입한 사람과 이전에 가입한
사람이 서로 다른 내용에 동의한 것이 됩니다. 어느 판에 동의했는지가 기록의 핵심입니다.
프런트 `constants/terms.ts` 의 `effectiveDate`(`"시행일자 2026년 8월"`)를 그대로 넣습니다.

**② `agreed` 가 `false` 인 것도 남깁니다.** 선택 약관을 거부한 것도 기록해야 합니다.
"물어봤고 거부했다" 는 사실 자체가 마케팅을 보내지 않았음을 증명하는 근거입니다.

**③ `ON DELETE CASCADE` 로 개인정보와 함께 파기됩니다.** 약관에 "탈퇴 후 30일" 이라고
적어 두었으므로 이 표에도 같은 기한이 적용되어야 합니다. 이 표만 남으면 적어 둔 것과 어긋납니다.
파기했다는 사실은 기존 `data_erasure_logs` 가 남깁니다.

### `TermsAgreement` 엔티티 (신규)

서버가 아는 약관 목록을 중첩 enum 으로 둡니다. 프로젝트가 이미 쓰는 방식(`User.Status`)입니다.

```java
public enum Type {
  SERVICE("service", true),
  PRIVACY("privacy", true),
  // 마케팅 동의를 필수로 하면 개인정보 보호법 제22조 제5항 위반임
  // (선택 동의를 거부한 이유로 서비스 제공을 거부할 수 없음)
  MARKETING("marketing", false);
```

칼럼은 `VARCHAR` 로 두고 이 enum 으로 검사만 합니다. PostgreSQL `ENUM` 타입으로 두면
약관을 늘릴 때 DB 타입을 고쳐야 하고, 약관을 접었을 때 이미 저장된 문자열을 읽지 못하게 됩니다.

### `SignupRequest` 확장

```java
@NotEmpty(message = "약관 동의 정보가 필요합니다.") @Valid
    @Size(max = 20, message = "약관 동의 정보가 올바르지 않습니다.")
    List<TermsAgreementRequest> agreements
```

`@Valid` 가 핵심입니다. **이게 없으면 목록 안쪽 요소의 제약이 검사되지 않아** `key` 가 비어
있어도 그대로 통과합니다.

### `AuthService.signup` — 확인 순서

```java
// 필수 약관 동의를 먼저 확인함
// 이메일·닉네임 조회보다 앞에 두어, 동의 없이 보낸 요청으로는 가입 여부를 알아낼 수 없게 함
Map<TermsAgreement.Type, TermsAgreementRequest> agreements = resolveAgreements(request);

String email = normalizeEmail(request.email());
if (accountRepository.existsByEmail(email)) {
  throw new CustomException(ErrorCode.DUPLICATE_EMAIL);
}
```

동의 확인을 중복 조회 **앞**에 둔 것이 의도입니다. 뒤에 두면 약관 없이 요청을 던져도
409(중복 이메일)가 돌아와서 가입된 주소인지 알아낼 수 있습니다.

모르는 `key` 는 버립니다. 프런트가 약관을 추가하고 서버가 아직 모르는 동안 가입 전체가
막히면 배포 순서에 따라 서비스가 멈추기 때문입니다. 반대로 필수 약관이 빠지는 것만 막습니다.

```java
boolean allRequiredAgreed =
    TermsAgreement.Type.required().stream()
        .allMatch(type -> resolved.containsKey(type) && resolved.get(type).isAgreed());

if (!allRequiredAgreed) {
  throw new CustomException(ErrorCode.TERMS_NOT_AGREED);
}
```

### `TermsAgreementRequest.agreed` 가 `Boolean` 인 이유

```java
// 선택 약관은 false 도 기록 대상이므로 "안 보냄" 과 "거부" 를 구분함
// 원시 타입 boolean 이면 null 이 조용히 false 가 되어 둘을 구분할 수 없음
Boolean agreed
```

### 프런트 — 동의 상태를 퍼널로 올림

`StepTerms` 가 체크 상태를 직접 들고 있었습니다. 단계를 옮기면 그 컴포넌트가 언마운트되어
**"다음" 뒤에 "이전" 을 누르면 체크가 전부 풀렸습니다.** 가입 요청에 동의를 담아 보내려면
`StepInfo` 도 그 값을 알아야 하므로, 상태를 `SignupFunnel` 로 올렸습니다.

결함 하나를 고치면서 사용성 문제도 함께 사라졌습니다.

```tsx
// SignupFunnel.tsx
const [checkedTerms, setCheckedTerms] = useState<Partial<Record<TermsKey, boolean>>>({});

<StepTerms checked={checkedTerms} onCheckedChange={setCheckedTerms} onNext={...} />
<StepInfo checkedTerms={checkedTerms} onPrev={...} onComplete={...} />
```

```typescript
// constants/terms.ts — 보낼 모양으로 바꾸는 함수
export const toAgreementPayload = (checked: Partial<Record<TermsKey, boolean>>) =>
  TERMS_DOCUMENTS.map((document) => ({
    key: document.key,
    version: document.effectiveDate,
    agreed: Boolean(checked[document.key]),
  }));
```

### 추가한 테스트

| 테스트 | 고정하는 것 |
| --- | --- |
| 필수 약관 미동의 → 400 | 서버가 다시 확인함 |
| 필수 약관을 `agreed: false` 로 → 400 | 보냈다고 동의한 것이 아님 |
| 약관 없이 보내면 `existsByEmail` 을 부르지 않음 | **확인 순서** (가입 여부 노출 방지) |
| 동의 기록 3줄 저장, 거부도 저장 | 선택 약관 거부 기록 |
| 모르는 key 는 버리고 나머지 처리 | 배포 순서에 안 막힘 |
| `agreed` 누락 → 400 | `Boolean` 로 둔 이유 |
| 파기 때 `deleteByUser_Id` 호출 | 30일 기한이 이 표에도 적용됨 |
| 회원이 없으면 동의 기록도 안 건드림 | 멱등성 |
| 컨트롤러: `agreements` 없으면 400 | 칸 자체 누락 |
| 컨트롤러: `key` 빈 문자열이면 400 | `@Valid` 가 안쪽까지 검사함 |

### 실제 확인

```
① 필수 약관 없음        → 400 {"message":"필수 약관에 동의해야 가입할 수 있습니다."}
② 필수 약관을 거부로    → 400 같은 응답
③ 정상                  → 201, user.id = 3
```

# 2. 조용히 깨지던 것 — 개인정보 파기 트랜잭션 (11부)

## 무엇이 문제였나

```java
// 고치기 전
@Transactional(readOnly = true)
public int purgeExpired(LocalDateTime now) {
  List<User> expired = userRepository.findByStatusAndWithdrawnAtBefore(...);
  for (User user : expired) {
    withdrawnDataEraser.erase(user.getId(), now);   // @Transactional (REQUIRED)
  }
}
```

`erase()` 의 `@Transactional` 은 기본 전파가 `REQUIRED` 입니다. 바깥에 **읽기 전용**
트랜잭션이 열려 있으면 거기에 **참여**합니다.

읽기 전용 트랜잭션에서는 하이버네이트가 `FlushMode.MANUAL` 로 두어 flush 를 하지 않습니다.
**delete 가 조용히 날아갑니다.** DB 가 read-only 를 강제하면 그 자리에서 예외가 납니다.

둘 중 어느 쪽이든 "파기가 성공한 것처럼" 끝날 수 있었습니다. 약관에 적은 30일 파기가
실제로는 일어나지 않는 상태입니다.

## 어떻게 고쳤나

양쪽에서 막았습니다.

```java
// WithdrawnDataPurgeService — 트랜잭션을 아예 걸지 않음
// 대상을 고르는 조회는 스프링 데이터가 호출마다 트랜잭션을 열어 주므로 따로 걸 필요가 없고,
// 지우는 일은 사람마다 eraser 쪽에서 새 트랜잭션으로 커밋됨
public int purgeExpired(LocalDateTime now) {
```

```java
// WithdrawnDataEraser — 부르는 쪽 사정과 무관하게 새 트랜잭션
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void erase(int userId, LocalDateTime now) {
```

`REQUIRES_NEW` 를 함께 넣은 이유는, 나중에 다른 곳에서 이 메서드를 트랜잭션 안에서 부를 때
같은 함정에 다시 빠지지 않게 하려는 것입니다.

## 실제 확인

`withdrawn_at` 을 31일 전으로 돌려놓고 서버를 띄웠습니다.

| | 파기 전 | 파기 후 |
| --- | --- | --- |
| `users` | 1 | **0** |
| `accounts` | 1 | **0** |
| `terms_agreements` | 3 | **0** |
| `data_erasure_logs` | 0 | **1** |

쓰기가 실제로 커밋됩니다.

# 3. 입력 상한 누락 (10부)

`WithdrawalRequest.password` 에 길이 상한이 없었습니다. `LoginRequest` 에는 있습니다.

```java
// LoginRequest — 상한 있음
@NotBlank @Size(max = PasswordValidator.MAX_LENGTH) String password

// WithdrawalRequest — 고치기 전, 상한 없음
@NotBlank(message = "비밀번호를 입력해 주세요.") String password
```

상한이 없으면 수 MB 짜리 문자열 하나로 유니코드 정규화와 **PBKDF2 10만 회**를 그대로 돌립니다.
탈퇴는 인증이 필요한 경로지만, 로그인한 계정 하나로도 서버를 붙잡아 둘 수 있습니다.

```java
// 고친 뒤
@NotBlank(message = "비밀번호를 입력해 주세요.")
    @Size(max = PasswordValidator.MAX_LENGTH, message = "비밀번호는 20자 이하여야 합니다.")
    String password
```

## `docs/deployment.md` — 보안에 영향 있는 어긋남

한 문서 안에서 서로 반대되는 안내가 있었습니다.

| 위치 | 내용 |

| 125행 | "`FORWARD_HEADERS_STRATEGY=framework` 는 `render.yaml` 에 이미 있습니다" |
| 322행 | "`FORWARD_HEADERS_STRATEGY` 는 쓰지 않습니다 ... 대시보드에 남아 있으면 지워야 합니다" |

125행을 고치고, 왜 쓰지 않는지와 예전 안내가 있었다는 사실을 함께 적었습니다.

# 5. 정의되지 않은 애니메이션 (14부)

```tsx
// Modal.tsx — 이 이름으로 애니메이션을 부르는데
className="... animate-[modal-in_150ms_ease-out]"
```

```bash
$ grep -rn "modal-in" frontend/src/
src/components/Modal.tsx:64:  animate-[modal-in_150ms_ease-out]
```

`@keyframes modal-in` 이 **어디에도 없었습니다.** 브라우저는 없는 애니메이션 이름을
조용히 무시하므로, 오류 없이 "아무 일도 일어나지 않는" 상태였습니다.

`src/styles/index.css` 에 넣었습니다. 배경 페이드인과, 움직임을 줄이도록 설정한 이용자를 위한
`prefers-reduced-motion` 도 함께 두었습니다.

```css
@keyframes modal-in {
  from { opacity: 0; transform: scale(0.96) translateY(-8px); }
  to   { opacity: 1; transform: scale(1) translateY(0); }
}

@media (prefers-reduced-motion: reduce) { ... }
```

빌드 결과물에 실제로 들어가는지 확인했습니다.

```bash
$ grep -o "modal-in" dist/assets/*.css
modal-in
```

# 6. 접근성 (14부·17부)

## `Input` — 오류 메시지가 입력칸과 연결되지 않음

`id` 는 붙여 두었는데 쓰지 않았습니다.

```tsx
// 고치기 전 — id 는 있지만 아무도 가리키지 않음
<p id={`${inputId}-error`} className="text-sm text-red-500">{error}</p>
```

화면을 못 보는 이용자는 테두리가 빨간 것도, 왜 틀렸는지도 알 수 없습니다. 입력칸과 설명이
따로 떠 있는 상태입니다.

```tsx
// 고친 뒤
const describedBy = error
  ? `${inputId}-error`
  : helperText ? `${inputId}-helper` : undefined;

<input
  aria-invalid={error ? true : undefined}   // false 면 속성 자체를 뺌
  aria-describedby={describedBy}
/>
```

## `Modal` — 포커스 트랩·`aria-modal`·제목 연결이 없음

고치기 전에는 `role="dialog"` 와 `id="modal-title"` 만 있었습니다. 빠진 것:

| 항목 | 없으면 |
| --- | --- |
| `aria-modal="true"` | 스크린 리더가 뒤에 깔린 내용도 함께 읽음 |
| `aria-labelledby` | 그냥 "대화상자" 로만 들림 (`id` 를 만들어 두고 연결 안 함) |
| 열 때 포커스 이동 | 키보드만 쓰는 이용자는 모달이 떴다는 것도 모름 |
| **포커스 트랩** | **Tab 이 모달을 빠져나가 뒤 화면의 버튼으로 넘어감** |
| 닫을 때 포커스 복원 | 포커스가 사라짐 |
| 닫기 버튼 이름 | SVG 는 읽히지 않아 그냥 "버튼" |

제목 `id` 를 `useId()` 로 바꿨습니다. 고정 문자열이면 모달이 두 개 열렸을 때 중복됩니다.

포커스 트랩에서 한 가지를 조심해야 했습니다.

```tsx
// 처음에 이렇게 썼다가 테스트가 전부 실패했음
.filter((element) => element.offsetParent !== null)
```

`offsetParent` 는 실제 레이아웃을 봐야 아는 값이라 **jsdom 에서는 언제나 `null`** 입니다.
그러면 포커스 가능 목록이 늘 비어서 트랩이 테스트 환경에서 통째로 동작하지 않습니다.
레이아웃에 의존하지 않는 검사로 바꿨습니다.

```tsx
.filter((element) =>
  !element.closest('[hidden]') &&
  element.closest('[aria-hidden="true"]') === null,
)
```

Tab 목록은 **누를 때마 다시 구합니다.** 미리 담아 두면 모달 안 내용이 바뀔 때 낡은 목록이 됩니다.

## `Button` — 기본 `type` 이 `submit`

```tsx
// 고친 뒤
function Button({ type = 'button', ... }) {
```

`<button>` 의 기본 `type` 은 `submit` 입니다. 폼 안에 둔 "취소", "주소 검색" 같은 버튼이
누르는 순간 폼을 제출합니다. 제출 버튼에만 `type="submit"` 을 적도록 기본값을 뒤집었습니다.
기존 제출 버튼들은 이미 `type="submit"` 을 명시하고 있어 동작이 바뀌지 않습니다.

## `<a>` 안의 `<button>` 중첩

```tsx
// 고치기 전 — HTML 명세가 금지하는 중첩 (a 안에 상호작용 요소)
<Link to="/login"><Button size="sm">로그인</Button></Link>
```

스크린 리더가 "링크, 버튼" 으로 두 번 읽고 Tab 이 두 번 멈출 수 있습니다.

버튼 스타일을 `components/buttonStyles.ts` 로 빼서 링크가 재사용하게 했습니다.
컴포넌트 파일에서 함수를 같이 내보내면 react-refresh 규칙(`only-export-components`)에
걸리므로 별도 파일로 두었습니다.

```tsx
<Link to="/login" className={buttonClassName({ size: 'sm' })}>로그인</Link>
```

`Header` 와 `StepComplete` 두 곳을 고쳤습니다. 새 탭으로 열기도 그대로 동작합니다.

# 7. 동작하지 않던 스타일 (14부)

```tsx
className="h-4 w-4 accent-emerald-600 focus-visible:ring-2 focus-visible:ring-emerald-500"
```

# 9. `strict` 모드가 꺼져 있었음 (13부)

`frontend/tsconfig.app.json` 에 `strict` 가 없었습니다. TypeScript 를 쓰는 이유의 절반이
빠져 있던 상태입니다. 특히 `strictNullChecks` 가 없으면 `null` 일 수 있는 값을 그냥 쓰는
코드가 컴파일을 통과하고 런타임에 터집니다.

즉 지금까지 운이 좋았던 것이 아니라, 검사만 꺼져 있었던 것입니다. 앞으로 들어올 코드를
막아 주는 것이 이 수정의 값입니다.

`tsconfig.node.json` 에도 켜고, `include` 에 `vitest.config.ts` 를 넣어 검사 대상에 포함했습니다.

# 14. CI (18부)

| 수정 | 이유 |
| --- | --- |
| `cache: maven` 추가 | 없으면 매번 의존성을 전부 내려받아 1~2분 더 걸림 |

## `CI Gate` 가 필요한 이유

`check` 잡의 이름은 matrix 로 만들어져 매번 달라집니다(`Check: frontend (node)`).
그 이름을 브랜치 보호의 필수 검사로 지정하면, **그 프로젝트를 건드리지 않은 PR 에서는
잡이 아예 생기지 않아** "Expected — Waiting for status to be reported" 로 영원히 merge 가
막힙니다.

건너뛴 잡(skipped)은 통과로 처리되지만, **생성되지 않은 잡은 아예 없는 것**이라 통과로
처리되지 않습니다.

```yaml
ci-gate:
  name: CI Gate
  if: always()
  needs: [detect, deploy-config, check]
  steps:
    - run: |
        if [ "${{ contains(needs.*.result, 'failure') }}" = "true" ]; then exit 1; fi
        if [ "${{ contains(needs.*.result, 'cancelled') }}" = "true" ]; then exit 1; fi
```

브랜치 보호에는 `CI Gate` **하나만** 넣으면 됩니다.

# 15. graceful shutdown (12부)

```yaml
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
server:
  shutdown: graceful
```

기본값(`immediate`)이면 재배포할 때 그 순간 처리 중이던 요청이 끊깁니다. 가입·탈퇴 같은
쓰기 요청이 중간에 잘릴 수 있습니다. Render 는 SIGTERM 을 보내고 잠시 기다리므로 그 시간을
이렇게 씁니다.

`spring.lifecycle` 을 기존 `spring:` 블록 **안에** 넣어야 합니다. 같은 YAML 문서에
`spring:` 키가 두 번 나오면 중복 키 오류입니다.

## 주목할 것

**`authStore.test.ts` 의 하드코딩 제거.** 저장소 키를 `const STORAGE_KEY = 'nanumi-auth'`
로 적어 두고 있었습니다. 키를 바꾸면 테스트가 조용히 엉뚱한 키를 보게 됩니다.
`authStore` 가 내보내는 `AUTH_STORAGE_KEY` 를 가져다 쓰도록 바꿨습니다.

**검증 규칙을 문구·순서까지 고정.** 백엔드 `EmailValidator` / `PasswordValidator` 와 같은
순서여야 하는 이유는, 순서가 다르면 프런트에서 지적한 것을 고쳐도 서버가 다른 것을 지적해서
두 번 고치게 되기 때문입니다. 예를 들어 `a@b.c` 는 형식(TLD 1자)도 틀렸지만 길이(5자)에서
먼저 걸려야 합니다.

**`useLogout` 이 `getState()` 로 읽는 이유를 고정.** 선택자로 받아 클로저에 담으면
재발급으로 토큰이 바뀐 뒤에도 옛 값을 보냅니다. 그러면 서버가 "없는 토큰" 으로 보고
재사용 공격으로 판단해 그 계정의 **모든 기기**를 로그아웃시킵니다.

**보이지 않는 문자는 코드 포인트로 적음.** `'행복​아파트'` 처럼 씁니다. 문자를 직접
붙여 넣으면 편집기가 지울 수 있고 커밋에서 사라질 수 있습니다.

**`cleanup()` 을 직접 불러야 했음.** `vitest.config.ts` 가 `globals: true` 가 아니라서
테스트 라이브러리의 자동 정리가 등록되지 않습니다. 모달은 `createPortal` 로
`document.body` 에 붙으므로, 정리하지 않으면 앞 테스트의 모달이 남아 다음 테스트에서
"같은 것이 두 개 보인다" 로 실패합니다.

# 앞서 잘못 보고한 것

가이드를 전달할 때 **"프런트 이메일 정규식이 백엔드보다 느슨하다"** 고 적었습니다.
이번에 두 파일을 나란히 놓고 대조한 결과 **틀린 지적이었습니다.**

```java
// backend EmailValidator
"^[A-Za-z0-9._%+-]+@[A-Za-z0-9-]+(\\.[A-Za-z0-9-]+)*\\.[A-Za-z]{2,}$"
```

```typescript
// frontend authSchema.ts
/^[A-Za-z0-9._%+-]+@[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)*\.[A-Za-z]{2,}$/
```

같습니다. 가이드 6-2 절에 적은 정규식(`^[a-zA-Z0-9]([a-zA-Z0-9._%+-]*[a-zA-Z0-9])?@...`)이
실제 코드와 다른 옛 형태였고, 그걸 기준으로 16-1 절에서 "고치라" 고 안내한 것입니다.
**가이드 쪽이 틀렸고 코드는 맞습니다.**

이참에 나머지 검증 규칙도 전부 대조했습니다.

| 항목 | 백엔드 | 프런트 | 일치 |
| --- | --- | --- | --- |
| 이메일 정규식 | 위와 같음 | 위와 같음 | ✅ |
| 이메일 길이 | 7~100 | 7~100 | ✅ |
| 이메일 검사 순서 | 빈값→공백→@개수→길이→ASCII→형식 | 같음 | ✅ |
| 비밀번호 길이 | 8~20 | 8~20 | ✅ |
| 비밀번호 검사 순서 | 빈값→공백→ASCII→길이→구성 | 같음 | ✅ |
| 닉네임 정규식 | `^[가-힣a-zA-Z0-9]{2,10}$` | 같음 | ✅ |
| SafeText 메시지 4종 | — | — | ✅ 문구까지 동일 |

# 이번에 손대지 않은 것

## 새 기능이라 별도 작업이 필요한 것

**비밀번호 재설정.** 비밀번호를 잊으면 복구할 길이 없어 새 이메일로 다시 가입해야 합니다.
실사용 전에 반드시 필요하지만, **이메일 발송 수단**(SMTP 또는 Resend·SendGrid 등)을
먼저 정해야 해서 결함 수정 범위를 넘습니다. 설계는 가이드 20-4 절에 적어 두었습니다.
`docs/deployment.md` 점검표에 항목으로 추가했습니다.

**프리뷰와 운영 DB 분리.** Vercel 프리뷰 배포가 Render 운영 백엔드를 그대로 부릅니다.
프리뷰에서 가입·탈퇴를 시험하면 운영 데이터가 바뀝니다. 스테이징 백엔드와 Neon 브랜치를
새로 만들어야 하는 인프라 작업입니다. 점검표에 추가했습니다.

**DB 장애 외부 감시.** `healthCheckPath` 가 `liveness` 라서 DB 가 죽어도 Render 는 정상으로
봅니다(Neon 유휴 중지로 멀쩡한 인스턴스가 재시작되는 것을 막으려는 의도적 선택).
UptimeRobot 등 외부 서비스 계정이 필요합니다. 점검표에 이미 있습니다.

**E2E 테스트.** Playwright 도입 + 배포 후 스모크 워크플로. 새 도구를 들이는 일입니다.

## 바꿀 값이 크고 지금 틀리지 않은 것

**`id` 를 `int` → `Long`.** 엔티티·DTO·리포지토리·테스트까지 광범위하게 번지는 리팩터링입니다.
`int` 최대 21억이고 JavaScript `number` 안전 범위(900조) 안에 들어가므로 **지금 틀리지 않습니다.**
회원이 21억 명이 되기 전에 바꾸면 됩니다.

**`password VARCHAR(83)`.** 해시 형식(`$nanumi${ver}${iter}$salt$hash`)이 정확히 83자라서
맞춘 값입니다. 반복 횟수를 7자리로 올리거나 해시 길이를 바꾸면 깨집니다. 지금은 맞고,
`NanumiPasswordEncoder` 가 형식을 바꿀 때 함께 보도록 주석이 있습니다.

**닉네임 길이 10 vs 컬럼 20.** 컬럼이 넉넉한 것은 문제가 아닙니다. 나중에 규칙을 완화할
여지입니다.

**`MyPagePage` 이름.** "MyPage 페이지" 라서 Page 가 두 번이지만 취향 문제입니다.
파일을 옮기면 import 가 번지는데 얻는 것이 이름뿐입니다.

## 컴포넌트 테스트를 일부만 추가한 이유

`Modal` 만 추가했습니다. 닫히는 경로가 3개이고 스크롤 락 정리와 포커스 트랩이 있어
**눈으로는 확인하기 어려운 로직**이 들어 있기 때문입니다.

`LoginForm` 등 폼 테스트는 `@testing-library/user-event` 가 필요합니다. 패키지를 새로
받아야 해서 이번에는 넣지 않았습니다. `Modal` 테스트는 이미 있는
`@testing-library/react` 의 `fireEvent` 만으로 썼습니다.

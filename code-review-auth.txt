[ 총평 ]

보안 기초는 상위권입니다.
 - PBKDF2 + per-password salt + 서버 전용 pepper
 - MessageDigest.isEqual 상수시간 비교
 - 미가입 계정에도 더미 해시를 돌려 응답 시간을 맞추는 타이밍 방어
 - 역직렬화(NFKC 정규화 + 불가시 문자 제거) 다음 검증(@SafeText)으로 이어지는 2단 XSS 방어
 - CSP / frame-options / HSTS / Referrer-Policy / Permissions-Policy 설정
 - 해시에 버전과 반복횟수를 기록해 파라미터 상향 시 자동 재해싱(upgradeEncoding)

문제는 "인증 수명 주기"가 절반만 구현되어 있다는 점입니다.
현재 상태로 배포하면 로그인은 되지만
  · 새로고침하면 즉시 로그아웃되고
  · 1시간 뒤에도 로그아웃되며
  · 로그아웃이나 탈퇴를 해도 토큰은 계속 살아 있습니다.

아래 심각도 순으로 정리했습니다.

  · 프론트는 zustand 메모리 저장(frontend/src/stores/authStore.ts:17)이라

2. 액세스 토큰과 리프레시 토큰을 구분할 수 없음
--------------------------------------------------------------------------------
위치 : backend/api/src/main/java/com/nanumi/api/security/JwtTokenProvider.java:69-79
       backend/api/src/main/java/com/nanumi/api/security/JwtAuthenticationFilter.java:29

createToken()은 만료시간만 다르고 클레임이 완전히 동일합니다.
따라서 Authorization: Bearer {refreshToken} 으로 보내면
JwtAuthenticationFilter가 그대로 통과시킵니다.

즉 리프레시 토큰이 14일짜리 액세스 토큰으로 동작합니다.
액세스 토큰 수명을 1시간으로 짧게 잡은 의미가 사라집니다.

조치
  claim("typ", "access" / "refresh") 를 넣고 필터에서 access만 허용.
  jti, iss 도 함께 넣어 두면 이후 토큰 무효화에 사용할 수 있습니다.

3. 탈퇴나 로그아웃을 해도 액세스 토큰은 최대 1시간 유효
--------------------------------------------------------------------------------
위치 : backend/api/src/main/java/com/nanumi/api/service/AuthService.java:123-153

logout()과 withdraw()는 상태 변경과 리프레시 토큰 삭제만 합니다.
필터는 서명과 만료만 확인하고 DB 상태를 전혀 조회하지 않습니다.

따라서 탈퇴 직후에도 기존 토큰으로 인증 API를 계속 호출할 수 있습니다.
리프레시 엔드포인트가 없는 현재로서는 로그아웃이
사실상 "프론트 state 비우기"에 불과합니다.

조치 (택 1)
  a) 액세스 토큰을 5~15분으로 줄이고 감수
  b) User.tokenVersion 컬럼을 토큰 클레임에 넣고 필터에서 대조
  c) jti 블랙리스트 (Redis)

4. X-Forwarded-For 무조건 신뢰, 로그인 잠금 100% 우회
--------------------------------------------------------------------------------
위치 : backend/api/src/main/java/com/nanumi/api/controller/AuthController.java:56-62

주석에 "이 헤더는 요청하는 쪽에서 지어낼 수도 있으므로,
믿을 수 있는 프록시 뒤에서만 의미가 있음" 이라고 직접 적어 두었으나
코드는 무조건 신뢰합니다.

  X-Forwarded-For: 1.2.3.4  -> 5회
  X-Forwarded-For: 1.2.3.5  -> 5회
  ... 헤더만 바꾸면 무제한

무제한 비밀번호 대입이 가능해집니다.
덤으로 attempts 맵에 항목이 무한 적재됩니다.
LoginAttemptService.java:120-125 의 cleanUp은 오래된 항목만 제거하므로,
방금 생성된 항목은 정리되지 않아 메모리 고갈(OOM)을 유도할 수 있습니다.

조치
  server.forward-headers-strategy 설정 + 신뢰 프록시 화이트리스트
  attempts 맵에 크기 상한(LRU) 추가

10. refresh_token 유니크 인덱스가 MySQL에서 생성되지 않을 수 있음
--------------------------------------------------------------------------------
위치 : backend/api/src/main/java/com/nanumi/api/entity/Account.java:52

@Column(unique = true, length = 1000)
utf8mb4 기준 1000자 = 4000바이트이고, InnoDB 인덱스 키 상한은 3072바이트입니다.
prod는 ddl-auto: validate 이므로 테이블을 수동 생성할 때 막힙니다.

더 근본적으로, 리프레시 토큰을 평문으로 저장하면 안 됩니다.
DB 유출 시 그대로 사용 가능한 자격 증명이 됩니다.

조치
  SHA-256 해시(64자 고정)로 저장하면 길이 문제와 유출 위험이 동시에 해결됩니다.

================================================================================
 [ 중간 ] 아직 결정되지 않은 정책과 기능 구멍
================================================================================

아래 4가지는 "로그인/회원가입 기능"의 필수 구성요소인데 통째로 빠져 있습니다.

 (1) 비밀번호 찾기 / 재설정
     현재는 비밀번호를 잊으면 탈퇴조차 불가능합니다(탈퇴에 비밀번호 필요).
     계정이 영구히 방치됩니다.

 (2) 비밀번호 변경
     유출을 인지해도 사용자가 취할 수 있는 조치가 없습니다.

 (3) 이메일 인증
     타인의 이메일로 가입이 가능합니다.
     (1)번 기능의 전제조건이기도 합니다.

 (4) 탈퇴 후 처리 정책
     email과 nickname 유니크 제약이 유지되어 같은 이메일로 재가입이 불가능합니다.
     또한 개인정보보호법상 탈퇴 회원 정보의 파기와 익명화 배치가 필요합니다.
     soft delete만 하고 방치해서는 안 됩니다.

그 외 정책 결정 사항

 · 계정 열거(account enumeration)
   로그인은 더미 해시까지 써 가며 방어했으나,
   회원가입은 "이미 사용 중인 이메일입니다" 로 존재 여부를 그대로 알려 줍니다.
   방어 수준을 통일할지 결정이 필요합니다.
   현실적으로 가입 UX 때문에 노출을 감수하는 것이 일반적이므로,
   감수한다면 로그인 쪽 방어의 목적을 문서에 명시해 두는 편이 좋습니다.

 · 회원가입에 rate limit이 없음. 스팸 가입이 무제한 가능합니다.

 · 다기기 로그인
   Account.refreshToken 컬럼이 1개라 새 기기에서 로그인하면 기존 기기가 끊깁니다.
   의도라면 문서화, 아니라면 refresh_tokens 별도 테이블 필요.

 · 닉네임 중복 검사가 대소문자를 구분
   abc 와 ABC 가 공존합니다. 이메일은 소문자 정규화했으나 닉네임은 하지 않았습니다.

 · 비밀번호 최대 20자는 요즘 기준으로 짧음 (패스프레이즈 차단)
   PBKDF2에 길이 제약이 없으므로 64~72자로 여유를 두는 것을 권장합니다.

   권한 분기가 생기면 문제가 됩니다.

 · 테스트
   검증기와 인코더 단위 테스트는 좋습니다.
   다만 AuthService, AuthController 테스트가 0건입니다.
   위에서 지적한 항목 중 상당수(중복 가입 경합, 탈퇴 후 토큰, 로그인 잠금)는
   통합 테스트 하나로 잡을 수 있습니다.
